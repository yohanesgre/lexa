Lexa · Implementation Plan

Dashboard → Project Status View

The dashboard at / stops listing projects and becomes the status detail view of the currently selected project. Project switching moves fully to the navbar switcher, which gains health dots + task counts. Backend untouched — the existing GET /api/dashboard payload is re-scoped client-side (Approach A).

01Plan — three phases, two gates

Wireframes are the source of truth and come first. Implementation is frontend-only; verification gates before and after.

Phase 1 — Wireframesdesigner

  • wireframes/src/dashboard.html → rewrite as project status view (header w/ health dot + ⋯ + New project; column WIP rows; project-scoped stats; project-scoped Needs Attention)
  • wireframes/src/partials/navbar.html → switcher rows gain health dot + trailing task count; navbar-project-switcher.html preview updated
  • flow-overview.html + index.html → dashboard node re-described, switcher node updated
  • Run bash wireframes/build.sh — never touch wireframes/dist/
wireframes/build.sh renders · annotations present · no dist hand-edits

Phase 2 — Frontend componentsdesigner + fixer

  • Extract ProjectSettingsModal.tsx from ProjectCard (name, description, GitHub repo, delete)
  • Rewrite app/routes/index.tsx → selected project's status; validateSearch for ?new=1 → CreateProjectModal
  • Expand ProjectSwitcher.tsx → health dot + task count; dashboard target = /; "Create new project" → /?new=1
  • app/lib/queries.ts → selector for selected project's health entry
  • Delete ProjectCard.tsx (modal already extracted)
tsc --noEmit passes · vitest run green · no backend/shared/docs edits

Phase 3 — Smoke verificationorchestrator

  • bun run dev:full → agent-browser snapshot checks (no vision): selected project renders, switcher from board/wiki, ?new=1 modal, empty state, stale-selection fallback
  • Wireframe build output spot-checked in browser
all smoke scenarios pass · acceptance pasted
Dependency: Phase 2 starts only after Phase 1's gate — code transcribes the wireframes exactly. Phase 3 runs after Phase 2's tsc gate.

03Data flow — one endpoint, two consumers

No backend change. The existing dashboard payload already carries per-project health; react-query shares it app-wide.

Server
① GET /api/dashboard · unchanged · per-project: health, wipSegments, taskCount, urgentCount, syncCount + urgentTasks[] + outOfSyncTasks[] (each w/ projectSlug)
Client cache
② react-query useDashboard() · one fetch, shared by navbar + page
Consumers
③ Dashboard / — filters projects by selectedSlug · urgent/out-of-sync lists filtered by projectSlug
④ ProjectSwitcher (all pages) — maps projects[] → health dot + task count
Selection
⑤ useProjectSelection · localStorage lexa:selectedProject · fallback chain: selected → stored → first project

05Edge cases

Explicit behavior decisions — no crash paths.

ScenarioBehavior
No projectsExisting dashboard-empty state (create CTA); switcher shows "No projects yet"
selectedSlug stale / deletedProvider fallback chain: selected → stored → first project; page re-renders, no crash
Selected project deleted while viewingRefetch returns without it → fallback kicks in on next render
Dashboard query errorExisting dashboard-error surface; never show empty state on error
?new=1 on empty instanceEmpty state still renders with its own CTA; modal opens only when projects exist
Switcher overflow (many projects)Menu max-height + scroll; existing hover/active/focus states unchanged
