Who holds which credential, how the machine listener + Forge daemon authenticate, and what happens when a key dies — the failure signatures and the recovery path for each. Built from the 2026-08-08 homestation outage (stale key → listener 401, orphaned machine → daemon register 409 FK).

01Credential inventory — who holds what

Three independent credentials. Each dies independently; each has its own recovery.

Runtime keyForge daemon~/.lexa/runtimes/<id>/env → LEXA_API_KEY (chmod 600)Daemon endpoints: register, daemon heartbeat, claim, log POSTsKey revoked/deleted, DB recreated, env file wiped
Server-side escape hatch: LXK_FORGE_DAEMON_TOKEN (server env) lets any caller pass x-forge-token on daemon paths (middleware.ts:30,63). Since 2026-08-08 daemons can no longer inherit it: the listener scrubs its shell env at spawn (scrubDaemonEnv, machine.ts) — the token remains only for manual daemon runs. A daemon whose env-file key is dead now exits 3 (case C) instead of being silently masked by an inherited token (the 2026-08-08 homestation incident).

02Lifecycle — registration → heartbeats → daemon

Read top to bottom. Each lane is one actor; arrows are HTTP calls.

Browser
Settings → Forge Runtimes → Setup runtime · lists machines (GET /forge/machines) · POST /forge/runtime-events (machine + agent CLI)
CLI listener
① login / register → POST /forge/machines/register · Bearer key · server mints machine row + secret, returns once → write machine-id + machine-secret (chmod 600)
② heartbeat loop · every 3s · POST /forge/machines/heartbeat (Bearer) · server upserts machine, returns project index → listener provisions ~/.lexa/projects/<id>/ workspaces
③ claim events · POST /forge/runtime-events/claim · x-machine-secret · server matches secret → event + one-time rawKey → write runtimes/<id>/env (LEXA_API_KEY) → spawn daemon → complete event
Forge daemon
④ register runtime · POST /forge/runtimes/register · Bearer env key (or x-forge-token) · inserts runtimes row (machine_id FK → machines)
⑤ daemon loop · POST /forge/daemon/heartbeat · claim task · spawn agent CLI · stream logs · terminal state (complete/fail)
Server + DB
middleware: rate limit → body check → Bearer resolve (key_hash) → route · daemon paths accept x-forge-token as alternate auth
tables: api_keys (key_hash) · machines (id, secret) · runtimes (id, machine_id FK) · runtime_events (status)
Key insight: the listener's three credentials are minted at different times — API key at login, machine secret at register, runtime key at each Setup-runtime event. Only the first two survive a re-login; the runtime key always comes from the web wizard flow.

Never trust lexa-cli machine restart alone for C/D — it respawns the daemon with the same dead env file. The env key is only replaced by the Setup-runtime event flow (or manual env edit).

04Daemon key-loss timeline — step by step

What actually happens, in order, when the daemon's key stops working (case C).

1Key dies: revoked in Settings / deleted / DB recreated — the api_keys row no longer exists.
2Daemon's next call (heartbeat/claim) → middleware Bearer lookup misses → 401 UNAUTHORIZED.
3Daemon exits with code 3 (auth failure). dies
4Listener sees daemon death → includes daemonErrors in next machine heartbeat → server writes runtimes.last_error.
5Settings renders the hint: "API key revoked — re-run Setup runtime" (matches "api key" in last_error). detected
6Admin re-runs Setup runtime → POST /forge/runtime-events (install, new key minted).
7Listener claims (x-machine-secret) → writes env.LEXA_API_KEY → kills old daemon → spawns new one.
8Daemon registers + heartbeats with the fresh key → runtime Online. recovered
Same 401 signature, different cause: if the listener (not the daemon) shows 401, that's case A — the listener's config.json key is stale, not the runtime env key. Check ~/.lexa/config.json against .env (compare hashes) before touching runtimes.
