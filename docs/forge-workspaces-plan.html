Forge Workspaces

Per-project sandboxes on the daemon machine. Agents get project files, project rule bundles, and a sealed HOME — and can no longer go hunting through the host.

The incident

why this exists

Continue · seed-task-f-14 "Integrate new furnace tilemap" · cancelled after 96s

The agent spawned in an empty ephemeral dir — no project files, no confinement. It went looking for the project on the host:

Root causes found

  • No workspace — run dir had only AGENTS.md + skill; nothing pointed at project files
  • No confinement — global opencode.json with permission: allow; bash unrestricted
  • Persona drift — runtime had no CLI agent → opencode defaulted to build

Fixes in this plan three layers

  • Workspace — persistent ~/.lexa/projects/<projectId>/, auto-provisioned
  • Rules — static orchestrator AGENTS.md + per-agent bundles + auto-discovered skills
  • Sandbox — per-run sealed HOME + tool-level deny rules

03

Workspace layout

~/.lexa/projects/<projectId>/
~/.lexa/projects/seed-proj-full/ ← daemon-owned · persistent · cwd of every run ├─ README.md ← seeded once: name + description + "clone repo here" ├─ AGENTS.md ← ORCHESTRATOR · static · project context + "your agent id is in your prompt" ├─ .agents/ │ ├─ agents/ │ │ └─ lexa/AGENTS.md ← every lexa-agent (default + custom) · refreshed per claim · never deleted │ │ └─ engine/AGENTS.md ← custom agent bundle │ └─ skills/ │ └─ continue/SKILL.md ← auto-discovered by opencode (path + frontmatter fixed) └─ .forge/ └─ home/<taskId>/ ← SANDBOX HOME · sealed per run · rm -rf'd after ├─ .config/opencode/opencode.json ← deny rules · only config (no global MCP/plugins) └─ .local/share/opencode/auth.json ← copied, chmod 600 (repo/ — operator clones or symlinks the project's repo here; its own AGENTS.md never loads: discovery traverses up, not down)

Why persistent files

  • All agents coexist statically — one project, many bundles, zero per-run root churn
  • No backup/restore dance, no crash-recovery of half-written rules
  • Settings edits refresh the bundle on the next run (claim is the source of truth)

Why sandboxed HOME

  • Agent never sees ~/.lexa/config.json (API key), ~/.ssh, or the global config
  • Global permission: allow, MCP servers, plugins — all excluded; deny rules are the only config
  • Agent state (sessions, auth copies, caches) dies with the run dir

One run, step by step

provider === opencode
1 claim
daemon receives task.projectId + agentName + rules + prompt
2 ensure workspace
mkdir -p ~/.lexa/projects/<projectId>/ — first use creates it (listener usually pre-provisioned it)
3 refresh rule bundles
overwrite .agents/agents/<agentId>/AGENTS.md + .agents/skills/<skillId>/SKILL.md from claim (idempotent, persistent)
4 seed sandbox
.forge/home/<taskId>/ ← deny opencode.json + copied auth.json (chmod 600)
5 spawn
opencode run "…prompt…" · cwd = workspace root · HOME + XDG_* = sandbox
6 agent works (contained)
bash denied · file tools scoped to workspace prefix · project read via repo/…
7 complete / fail / cancel
result posted · finally: rm -rf .forge/home/<taskId>/ — nothing else touched

Multiple agents, one workspace FIFO, never concurrent

One runtime = one task at a time (claim → await run → claim). A queue of tasks with different lexa-agents runs sequentially — each run's prompt points at its own persistent bundle; nothing at the root changes between runs. Two machines → independent copies. One machine, two opencode runtimes → impossible (invariant: one runtime per agent CLI).

Task: Continue Agent: Lexa (id lexa) — read .agents/agents/lexa/AGENTS.md and follow it exactly. Document context: Task: Integrate new furnace tilemap Description: Waiting for art to deliver final tile sheets (ETA next sprint). All code is ready — just need assets. Your working directory contains AGENTS.md (project rules) and .agents/ (your rules and skills) — follow them. Output rules: - Output ONLY the requested text. Nothing else. - Preserve the document's existing structure and inline formatting; mirror the selection's style exactly. - Format as clean, well-structured Markdown. Your output becomes the whole document (converted to rich text), so make it beautiful: - Use ## / ### headings (never H1), short scannable paragraphs, bullet lists for parallel points, numbered lists for steps, task lists for checklists, bold key terms, code spans for technical names. - Put code samples in fenced blocks with a language tag: ```ts, ```sql, ```bash, ```json. - No narration, no explanations, no status updates, no 'Here is...'. Never wrap the whole output in a markdown fence. - If the linked sources contradict the document, prefer the sources.
