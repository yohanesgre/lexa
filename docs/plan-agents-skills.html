Lexa · Design Plan

Agents + Skills for Forge

Forge prompt management: named agent rule bundles, skill operations, and claim-carried delivery — the server hands each task's rules to the daemon inside the claim response. The host keeps no store, so it can never drift.

Status · Final docs/plan-agents-skills.html No sync layer Wireframes first No scope creep
§0

Concept

Agent

  • Named rule bundle: name, description (display-only, never reaches the agent), instructions
  • Builtin Lexa (default) + custom, admin-created
  • Global — not project-scoped

Skill

  • Named operation bundle, same shape
  • Builtins: Continue · Rewrite · Summarize · Expand · Fix grammar (seeded from ACTION_PROMPTS)
  • Custom, admin-created · Global

Binding

  • Many-to-many via forge_agent_skills
  • Seed: Lexa ↔ all 5 builtins
  • Custom agents start empty

Popover

  • Agent chips (default Lexa) → dependent Skill chips
  • Runtime picker per task · Additional prompt textarea per run

Delivery

  • Rules ride the claim response: agentMarkdown + skillMarkdown
  • Daemon writes them into the run dir; CLI reads them natively

Freshness

  • Edits apply to the very next task — by construction
  • No store, no sync, no drift, no notification states
Accepted tradeoff: hermes / command-code do not read AGENTS.md natively — they run on task context + output contract (degraded rule fidelity). Full fidelity is for AGENTS.md-capable CLIs (opencode).

Dropped: project memory · host-side sync store, events, and sync-health notifications (their failure mode — drift — no longer exists; offline hosts are already surfaced) · Backlog: artifacts, retention.

§1

Host layout

Single root ~/.lexa/ (env LEXA_DIR override), chmod 700. Works on Linux + macOS (os.homedir(), same pattern as ~/.agents/). Everything the runtime host stores lives here — config, machine identity, runtime envs, and per-run workdirs.

~/.lexa/
├── config.json                  ← login creds (600) · was ~/.config/lexa-cli/config.json
├── machine-id                   ← · was ~/.config/lexa-cli/machine-id
├── env                          ← daemon bootstrap env (600) · was ~/.config/lexa-forge/env
├── runtimes/<id>/env            ← per-runtime env (600) · was ~/.config/lexa-forge/runtimes/<id>/env
└── runs/<taskId>/                ← per-task workdir, ephemeral (cleaned after the run)
    ├── AGENTS.md                 ← agent rules, written from the claim payload
    ├── .agents/<skillId>/SKILL.md ← skill rules, written from the claim payload
    └── <anything the agent writes>

Workdir is ephemeral by design: explicit cleanup after complete / fail / cancel. The server is the single source of truth for rules — the host is stateless between runs. ~/.local/share/lexa-forge/ (listener install + systemd unit) stays where it is — installation data, not runtime state.

Migration — migrate and delete, no fallback. On listener boot and lexa-cli login: if the old dirs (~/.config/lexa-cli/, ~/.config/lexa-forge/) exist → move their contents into ~/.lexa/ (rename, same user/fs), delete the empty parents. New path wins if both exist. Migrate before reading config. Stale-version risk accepted: old binaries recreated after migration can't see the new state — upgrade all components together.

§5

Listener & Daemon

Listener scripts/cli/machine.ts — unchanged from today

  • Boot: migrate old ~/.config/lexa-* dirs into ~/.lexa/ — move, delete empty parents, no fallback
  • Heartbeat loop (3s): machine + agent/model catalogs
  • Claim machine events: install / update / remove — env write (~/.lexa/runtimes/<id>/env), daemon child spawn / restart / kill
  • No sync routine, no boot sync, no syncVersion — nothing new

Daemon scripts/forge/daemon.ts

  • Workdir: join(LEXA_DIR, "runs", task.id) — replaces /tmp/lexa-forge/<taskId>
  • Pre-spawn: write AGENTS.md from agentMarkdown + .agents/<skillId>/SKILL.md from skillMarkdown — no fetch, no gap-fill
  • Explicit cleanup of the run dir after complete / fail / cancel
  • Prompt per §4 — context + output contract + pointer line
  • Runs serialized in poll loop (daemon.ts:213-229) → seeding race-free

Delivery — claim-carried rules

DASHBOARD
SERVER
DAEMON
AGENT CLI
DASHedit agent / skill → save
SRVrows updated — nothing to propagate (no store, no events, no versions)
DMNnext claim → response carries agentMarkdown + skillMarkdown built from the current rows
DMNwrite AGENTS.md + .agents/<skillId>/SKILL.md into the run dir

DMNresult reported → run dir cleaned up

Freshness is by construction: an edit applies to the very next task. There is no state to be out of date, so there is nothing to notify about — the only failure mode is an offline host, already surfaced in the runtimes table.

§9

Verification gates

  • ⌁tsc --noEmit clean · vitest run clean
  • ⌁Migration on fresh DB + existing DB — backfill correctness (old tasks → correct skill + 'lexa' agent)
  • ⌁Claim carries rules: edit an agent → the next claim's agentMarkdown reflects it; run dir gets AGENTS.md + .agents/<skillId>/SKILL.md
  • ⌁Daemon: workdir seeded from claim payload only; run dir removed after complete / fail / cancel (no leftovers)
  • ⌁Popover: agent switch resets skill list; empty-skills disables Generate; run uses chosen agent + skill + extraPrompt
  • ⌁Offline host: claim simply fails until online — no catch-up, no sync dependency
  • ⌁Smoke via bun run dev:full
