Forge Runtimes
Machine-First Setup Flow

The CLI registers the machine with the server the moment you log in, and the web wizard installs runtimes onto that machine through server-mediated events — one machine, many runtimes, one daemon each.

lexa-cli machine registry setup events web wizard multi-runtime
What changed

From "CLI is the target" to "machine is the target"

Before (v1)

  • The wizard targeted a logged-in CLI; presence was a listener-id heartbeat.
  • The old direct listener install path provisioned a daemon directly — a second path that drifted from the wizard.
  • One daemon per machine, env in a single file, systemd units per daemon.

Now (v2)

  • After login, the CLI always listens and registers the machine (persisted machine-id, heartbeat). No extra command.
  • The wizard lists registered machines and installs runtimes onto them via setup events.
  • Events-only install: machine install only ensures the listener; every runtime daemon comes from the web.
  • One machine, many runtimes — one daemon child per agent CLI, managed by the listener.

The contract

Setup event — machine + agent CLI

POST /api/forge/runtime-events 
{
  "machineId": "3f2a1c…",
  "action": "install",          // install | update | remove
  "agentCli": "opencode",       // managed CLI
  "apiKeyId": "…",
  "rawKey": "lxk_…"             // in memory only, never SQLite
}
→ 201 RuntimeEvent
Machine-scoped claim

Only the target machine claims it

POST /api/forge/runtime-events/claim
{ "machineId": "3f2a1c…" }
→ { event, rawKey } | null

The claim is scoped by machine — a machine can never pick up another machine's event. Status flow: pending → claimed → completed | failed (2-min reclaim if a listener dies mid-install). Update/remove events carry no raw key.

The always-on receiver

Listener owns the daemons

for (;;) {
  machineHeartbeat(machineId, hostname)   // presence
  ev = claimEvent(machineId)               // this machine only
  if (ev) handleSetupEvent(ev, rawKey)      // install/update/remove
  sleep 3s
}

install/update → write ~/.config/lexa-forge/runtimes/<runtimeId>/env (per-runtime, chmod 600) → spawn daemon.ts as a child with that env → track in a Map<runtimeId, Child> → POST complete.

remove → kill the matching agent CLI child, delete its runtime dir. On listener exit, all children are killed; on restart, the listener re-reads the runtime dirs and respawns each daemon (crash recovery without systemd).

catalogs → the listener runs each installed CLI's model/agent listing commands and sends the results in the machine heartbeat. The daemon only reports liveness and MCP status.

Per-runtime env 
~/.config/lexa-forge/
└── runtimes/
    ├── opencode/
    │   └── env     # chmod 600
    └── command-code/
        └── env

~/.local/share/lexa-forge/
└── daemon.ts       # copied once

One daemon process per runtime, each spawned with its own env file. No per-runtime systemd units. Runtime Settings consume catalogs reported by the listener.

The core interaction

Install event — full sequence

Web wizard
Lexa server
CLI listener
Daemon child
1 · pick machine (from GET /machines) + choose agent CLI
2 · create API key — raw returned once, auto-copied
3 · POST /runtime-events { machineId, action, agentCli, apiKeyId, rawKey }
server verifies key hash + machine; raw key held in memory only
4 · POST /runtime-events/claim { machineId } → event + rawKey (one-time)
writes per-runtime env, spawns daemon.ts child, discovers CLI catalogs
5 · POST /runtime-events/:id/complete (or /fail)

The wizard polls the event while this happens; every transition (pending → claimed → completed) is visible in Verify.

One machine, many runtimes

Installing a second agent CLI

Scenario

homestation already runs opencode

homestation
online · 2 runtimes
opencode · deepseek-v4-flash command-code · claude-sonnet-4-5

The wizard lists the machine's existing runtimes so you can add another agent CLI without touching the first. Each install event spawns a separate daemon child with its own env + runtime id.

Isolation
  • Each runtime has its own env file + process.
  • Restarting one never affects the others.
  • A remove event kills just that child.
  • The Forge task queue routes by runtime id.
Lifecycle, both directions

Delete a runtime = despawn its daemon

Removal is an explicit action from the runtime list. It stops the daemon child on the machine; offline runtimes are never auto-removed.

What happens

DELETE /forge/runtimes/:id

1. server looks up the runtime's machine_id
2. creates a remove runtime-event
   targeting that machine
3. deletes the runtime row (UI shows it gone)
4. listener claims the remove event → kills
   the daemon child process tree
5. deletes ~/.config/lexa-forge/runtimes/<id>/
6. POST /runtime-events/:id/complete
Machine offline?

Removal is blocked

If the machine is offline, the server returns MACHINE_OFFLINE. The runtime stays in the list and the UI offers a restart/listener recovery guide.

  • No automatic row deletion.
  • Run lexa-cli machine listen on the machine.
  • Once online, explicit Remove can safely despawn the child.
Why it matters

A stale daemon would keep polling the task queue and hold credentials. The listener closes the loop only after the target machine confirms presence: install and explicit remove are symmetric events.

Secrets handling

Where the key lives (and never lives)

At rest

SQLite

SHA-256

API keys are stored hashed only. The raw value can never be read back — that's why the wizard always creates a fresh key for each install.

In flight

Server memory

5 min TTL

The raw key lives in an in-memory store with a 5-minute TTL and is deleted at claim — a single delivery.

On disk

Per-runtime env

chmod 600

The listener writes the delivered key into the runtime's env file, readable only by the user. The daemon child authenticates with it.

  • One-time delivery: a claimed event's raw key is removed from memory; a re-claim returns null.
  • Machine-scoped claims: the listener can only claim events addressed to its own machine id.
  • Credential fallback chain: env → ~/.config/lexa-forge/… → ~/.config/lexa-cli/config.json, so a manual daemon run uses your saved login.
Final step in detail

Verify — three states, zero guesswork

Waiting

Event pending / claimed

Spinner + "Waiting for the machine's listener…". Polls every 4s. The state machine is visible — no dead-end silence.

Success

Completed + heartbeat

"Runtime is online" — the event completed and a runtime with the chosen agent CLI heartbeats on that machine. Ready for Forge tasks.

Failure

Event failed

Shows the listener's error verbatim (e.g. agent CLI not found) with a pointer to the listener log.

Self-healing

The Machine gate keeps polling after a failure — fix the listener, and Continue unlocks without a reload. A late daemon heartbeat flips the spinner to success.

Recap

One flow, machine-first

CLI

Machine agent

lexa-cli login --url … --key …
lexa-cli machine listen        # registers machine, then waits
lexa-cli runtime list          # server-side runtimes view
lexa-cli machine logs          # listener journal

The CLI is a passive machine agent. machine install only ensures the listener; daemon installs arrive as setup events.

Web

Setup wizard

Settings → Forge Runtimes → Setup runtime
Machine → Agent CLI → Key + Send → Verify

Setup installs the runtime identity. After its first heartbeat, the runtime row exposes CLI-reported agents and provider/models for Settings configuration. Multiple runtimes per machine supported.

Both sides converge on the same contract — machines, runtime-events (machine + agent CLI), runtimes (daemon task surface + CLI catalogs). The web never talks to your machine directly; the listener is the bridge, and it owns the daemon children.
